Idea controller — how the store talks to IndexedDB

ideas-cache.ts and ideas-cache-controller.ts are the two halves of one controller. The zustand store is the single source of truth; it announces every change as an IdeasCacheMessage and never touches Dexie. The controller consumes those messages, writes them in one transaction, and acks them. On boot it does the reverse: it reads IndexedDB and seeds the store.

The queue

zustand state, not a real channel
  • Every mutating action appends one message
  • seq is monotonic — it is the ack token
  • Nothing is queued until activeUserId is known
  • Survives renders; dies with the tab
3

Controller

lib/outbox/ideas-cache-controller.ts
  • start() — one store subscription, module scope
  • flush() — drain, write, ack; serialised by a semaphore
  • after a local write: requestOutboxSync() → permanent store
  • hydrate(userId) — flush, then read, then seed
  • Owns ordering; sync owns the network
4

Adapter

lib/outbox/ideas-cache.ts
  • applyCacheMessages() — one Dexie transaction
  • readCachedIdeas(userId)
  • toCachedIdea / toIdea — tags JSON round trip
  • Stateless; no subscription, no locks

Steady state the pump

// any store write: upsertIdea / upsertIdeas / removeIdea / addPendingIdea / markPendingSynced / reset
store write
  → cacheOutbox.push({ seq: ++cacheSeq, message })
  → zustand subscriber fires            // registered once by cache.start()
  → Effect.runFork(flush)
       Semaphore.withPermits(1)             // a second flush WAITS, it does not skip
         loop
           queue      = store.cacheOutbox
           if empty   → return
           throughSeq = queue[last].seq
           ApplyCacheMessages(queue.map(m))  // ONE Dexie transaction
           store.ackCacheMessages(throughSeq) // drop only what was written
       // outside the permit
       if a local idea was persisted → requestOutboxSync()
         → sync.ts POSTs the outbox to /api/ideas, then the store
         //   emits `replace`, which flushes the permanent row into the cache

Messages queued while the write is in flight carry higher seq values, so the ack leaves them for the next pass. A failed write acks nothing, so the messages are still queued — the next store change re-triggers the pump.

Message contract 4 types, 4 store actions

MessagePayloadDexie effectEmitted by
upsert userId, ideas[], local? db.ideas.bulkPut(rows) upsertIdea, upsertIdeas, addPendingIdea (local: true)
replace userId, localId, idea delete(localId) then put(serverIdea) markPendingSynced(localId, serverIdea)
remove userId, ideaId db.ideas.delete(id) removeIdea(id) (permanent delete, and the optimistic revert path)
clear userId where("userId").equals(…).delete() reset()

Order inside one transaction is load-bearing — replace deletes before it writes — which is why the loop is sequential and no-await-in-loop is disabled on purpose in the adapter.

Flow A create — local first, then server

QuickCapture
  create(content)                          hooks/use-ideas.ts — no fetch in here
    SaveIdeaLocally(content, userId)       ── outbox row ONLY (durable intent)
    store.addPendingIdea(localIdea)        ── store write + message #1 upsert(local)
      → card renders immediately, marked pending
    cache.flush()                          ── local commit
      ApplyCacheMessages([#1])             → db.ideas row written by the controller
      ack(#1)
      tap → requestOutboxSync()            ── local save done, now the permanent store
        syncOutbox()
          GetPendingItems()
          POST /api/ideas { content, client_id: localId }
            ok  → MarkSynced(localId)          → outbox row deleted
                  store.markPendingSynced()    ── store write + message #2 replace
                    → local row swapped for the server row (same id)
            offline → returns before reading the outbox; stays pending

create() returns once the idea is on disk — the server round trip is requestOutboxSync's job, triggered by the controller. There is no separate online path: offline captures are the same code with syncOutbox no-op'ing.

Flow B offline create, then reconnect

create(content) while navigator.onLine === false
  SaveIdeaLocally → db.outbox (status: "pending")
  store.addPendingIdea → message upsert(local)
  cache.flush → db.ideas row
  tap → requestOutboxSync → syncOutbox → offline: returns immediately
    → nothing marked failed, retry budget untouched

window "online" → requestOutboxSync()
  SyncService.syncOutbox()                 lib/outbox/sync.ts
    GetPendingItems()                      → outbox where status === "pending"
      POST /api/ideas { content, client_id }
        ok    → MarkSynced(id)             → outbox row deleted
                store.markPendingSynced()  ── store write + message replace
        401   → MarkFailed(id, "Auth error")   → no retry, cannot fix itself
        5xx / network → bounded backoff retry, then MarkFailed

Hydration reads the outbox with anyOf("pending","failed"), so a failed idea keeps rendering as pending instead of disappearing, and outboxItemToIdea rebuilds the card if the db.ideas write never landed. syncOutbox still only retries pending rows.

Flow C hydrate: IndexedDB → store

useIdeas effect [userId]                     hooks/use-ideas.ts
  identity.setCachedUserId(userId)
  cache.hydrate(userId)                    IdeasCacheController
    flush()                                ← drain the queue FIRST
    ReadCachedIdeas(userId)                → every cached row for this user
    GetUnsyncedItems()                     → outbox pending + failed
    store.hydrate({ userId, ideas, unsyncedIds })
                                           ── store write, NO message
      same user  → merge into whatever SWR already fetched
      new user   → replace the list outright

window "focus" → hydrateIdeasCache(userId)  same path, picks up external tabs
Why flush before read. Anything still queued is newer than what is on disk. If hydrate read first, the write would land afterwards and the just-read snapshot would be stale — and hydrate would then seed the store from stale rows. The semaphore is what makes "flush, then read" trustworthy: a concurrent flush waits its turn instead of returning early.

Short version. The store is the only source of truth and the only writer of ideas. It publishes typed messages; the controller applies them to IndexedDB and acks by seq. A capture is durable as soon as its outbox row exists, and once the controller has written it locally the controller asks the sync service to push it to the permanent store. On boot the controller reads IndexedDB and seeds the store. Rendering never reads Dexie, and persistence never reads the store's list.
Two things this flow needed. saveIdeaLocally writes only db.outbox, so db.ideas has exactly one writer (the controller) and the outbox row is what survives a crash mid-capture. And syncItemWithRetry uses a bounded schedule — the previous Effect.repeat with Schedule.concat(recurs(n), exponential) never finished, so every capture re-POSTed forever, the syncing guard stayed stuck on, and (before client_id was honoured) each repeat created a duplicate idea.
